# Library API Specification

The `xdg-thumbnail` library provides reusable primitives for applications that need to read, validate, inspect, install, record failure entries for, or safely remove Freedesktop thumbnail cache entries.

The library crate supports Unix-like XDG desktop environments only. Unix path bytes, Unix file metadata, Unix permissions, and XDG cache semantics are part of the public contract; non-Unix targets must fail during crate compilation with a clear unsupported-target diagnostic instead of exposing runtime fallbacks that could approximate incompatible cache identities.

## Public API Goals

- Make spec-compatible thumbnail path calculation straightforward.
- Make thumbnail URI canonicalization explicit and shared by path calculation, metadata comparison, and validation.
- Use the same canonical thumbnail URI bytes for hashing, metadata comparison, and validation.
- Provide canonical URI constructors for local filesystem paths and shared-repository child filenames, while allowing callers that own non-local or virtual backends to choose a stable absolute original identity URI that the library validates and preserves without changing the identity used for hashing.
- Allow applications to validate cached thumbnails without duplicating PNG metadata parsing.
- Allow applications that own their own rendering or decoding stack to install spec-compatible personal-cache thumbnails without duplicating Freedesktop PNG metadata, permission, and atomic-save rules.
- Allow management tools to inspect cache entries without embedding CLI cleanup policy into the library.
- Allow management tools to request safe removal of inspected cache entries without reimplementing thumbnail-cache path containment and symlink checks.

## Core Capabilities

The library should expose APIs for:

- Resolving the personal thumbnail cache root.
- Constructing canonical personal-cache `file:` original URI identity strings from absolute local path bytes without lossy path conversion. Callers may resolve relative user input before calling this constructor, but the library owns the canonical URI identity used for hashing, `Thumb::URI`, metadata comparison, and validation.
- Constructing canonical personal-cache `file:` original URI identity strings from textual local file URI input as a separate path from the absolute-path constructor, accepting the `file:` scheme and `localhost` authority case-insensitively, normalizing local authorities to canonical lowercase `file:///...`, and rejecting or reporting non-local `file:` authorities as not directly checkable unless an explicit resolver is added.
- Constructing canonical shared-repository original URI identity strings only for direct child originals represented by `./`-prefixed relative URIs.
- Accepting caller-selected stable absolute original identity URIs for non-local and virtual backends, rejecting `file:` identities in this constructor so local file identities cannot bypass library-owned canonicalization, validating that accepted values can be thumbnail URI identities, and preserving the supplied identity bytes for hashing and metadata comparison.
- Computing the personal-cache path for an accepted absolute original URI identity and requested thumbnail namespace through `PersonalCacheRoot::cache_entry_path`.
- Returning computed cache paths as pure path-calculation results that do not imply file existence, metadata validity, or display safety.
- Looking up existing thumbnails as validated path results after opening the candidate PNG without following symlinks and verifying identity metadata, freshness metadata, PNG conformance, and namespace dimensions, while documenting that callers that reopen the returned path accept a post-validation replacement race.
- Looking up existing thumbnails as display-grade validated PNG byte results that contain the exact cache file content that the library opened without following symlinks and validated, plus the corresponding path and metadata facts. This is the preferred encoded-file surface for thumbnail views and other display paths that should not duplicate PNG metadata parsing or reopen by path after validation; callers that need a filename should request the separate validated path surface.
- Looking up existing thumbnails as decoded tightly packed RGBA8 pixel buffers after the same no-follow cache read and validation policy used by validated path and PNG bytes lookup. This surface is for callers that want to draw the cached thumbnail directly without accepting the replacement race of path reopening or decoding PNG bytes themselves.
- Computing shared-repository cache paths only from an explicit shared repository context that includes the repository root, the direct child original filename, and the shared `./`-prefixed URI used for hashing and metadata comparison.
- Representing cache namespaces separately for successful thumbnail sizes and program-version failure entries.
- Parsing thumbnail PNG metadata while exposing crate-owned bit-depth and color-type enums rather than `png` crate types.
- Representing `Thumb::MTime` as non-negative whole Unix epoch seconds through `UnixMtimeSeconds`. Public typed timestamp values store `u64`, expose `as_u64()`, and provide fallible signed conversion for callers that receive backend timestamps as `i64`; negative metadata values are invalid syntax, not stale metadata.
- Exposing typed thumbnail metadata accessors for `Thumb::MTime` and `Thumb::Size` so callers can distinguish missing metadata from invalid syntax. Lossy convenience accessors may still return `None` for both missing and invalid values when that is sufficient.
- Writing successful personal-cache thumbnail PNG metadata and final cache PNG output from a caller-provided readability-confirmed original identity and caller-provided rendered thumbnail bytes.
- Installing successful personal-cache thumbnails atomically under the resolved personal cache root from a readability-confirmed original identity and rendered thumbnail bytes after normalizing supported PNG renderer output, including cache-size downscaling when needed, to the final cache PNG format.
- Inspecting whether successful thumbnails are 8-bit non-interlaced PNG files with full alpha support and dimensions that fit the requested size class.
- Checking whether a personal-cache thumbnail is valid for a given original by verifying required `Thumb::URI` and `Thumb::MTime` metadata and verifying `Thumb::Size` when present.
- Checking shared-repository thumbnails with a separate validation context where the shared repository root and direct child original filename are explicit, present `Thumb::URI`, `Thumb::MTime`, and `Thumb::Size` values are verified, but missing `Thumb::URI` or `Thumb::MTime` does not automatically make the entry invalid.
- Iterating cache entries from known thumbnail directories. Personal-cache inspection APIs use `NonstandardEntryPolicy` instead of a boolean flag: `Exclude` skips nonstandard filenames and `Include` reports them as invalid entries with `NonstandardFilename`. The default policy is `Exclude`.
- Returning policy-neutral inspection facts for cache management tools, including thumbnail timestamps and whether metadata inspection preserved access time.
- Distinguishing inspection facts precisely enough that callers do not have to infer cleanup policy from a coarse invalid state, including whether a standard cache filename's hash identity does not match the stored canonical `Thumb::URI`.
- Returning cache entry handles that identify entries discovered by library iteration and can remove those entries safely when the caller has already made a deletion decision.
- Reading shared thumbnail repositories without modifying them, including read-only shared path lookup, PNG bytes lookup, and inspection results that do not expose removal handles.
- Writing opt-in failure entries under `fail/<program-version>/` when the caller explicitly supplies the failure namespace and a readability-confirmed original identity.

The public API should hide commodity implementation details from callers where possible. Callers interact with canonical original URI and cache path types rather than parser-specific URL objects or hash implementation details. Public URI newtypes may expose `thumbnail_file_name()` as a Freedesktop-facing cache filename helper, but must not expose hash stems or digest internals directly. The public URI newtypes are named around the original identity they represent: `PersonalOriginalUri`, `SharedRelativeOriginalUri`, and `OriginalUriIdentity`. The public personal-cache root type is `PersonalCacheRoot`. Shared repository lookup freshness and metadata acceptance inputs are grouped in `SharedOriginalFacts`, which carries `metadata_policy`, optional `mtime`, and optional `original_byte_size`; policy-neutral shared inspection uses policy-free `SharedOriginalMetadata` so an unused lookup policy is not accepted there. `SharedOriginalMetadata::new()` creates empty metadata facts, `with_mtime(mtime)` and `with_original_byte_size(size)` add known optional facts fluently, and `SharedOriginalFacts::new(policy, metadata)` combines a metadata acceptance policy with policy-neutral metadata facts. Pure path calculation is named `PersonalCacheRoot::cache_entry_path`. Validated personal lookup is named `PersonalCacheRoot::lookup_thumbnail_path`, `PersonalCacheRoot::lookup_thumbnail_png_bytes`, or `PersonalCacheRoot::lookup_thumbnail_rgba8`, matching shared-repository `SharedRepositoryContext::lookup_thumbnail_path`, `SharedRepositoryContext::lookup_thumbnail_png_bytes`, and `SharedRepositoryContext::lookup_thumbnail_rgba8`. Personal and shared lookup methods take the original facts before the thumbnail size. Successful personal-cache installs are named `PersonalCacheRoot::install_thumbnail_path`, `PersonalCacheRoot::install_thumbnail_png_bytes`, `PersonalCacheRoot::install_thumbnail_raw_path`, and `PersonalCacheRoot::install_thumbnail_raw_png_bytes`; failure-entry writes are named `PersonalCacheRoot::write_failure_entry_path` and `PersonalCacheRoot::write_failure_entry_png_bytes`, and take the readability-confirmed original identity before the failure namespace. Owned install and failure-entry requests keep output-specific execution names such as `PersonalThumbnailInstallRequest::install_path`, `PersonalThumbnailInstallRequest::install_png_bytes`, `PersonalThumbnailRawInstallRequest::install_path`, `PersonalThumbnailRawInstallRequest::install_png_bytes`, `FailureEntryWriteRequest::write_path`, and `FailureEntryWriteRequest::write_png_bytes`. Owned personal lookup requests use `PersonalThumbnailLookupRequest::lookup_path`, `PersonalThumbnailLookupRequest::lookup_png_bytes`, and `PersonalThumbnailLookupRequest::lookup_rgba8`; owned shared lookup requests expose the same output-specific execution names. Validated personal lookup returns `PersonalThumbnailLookup<T>`, with path, PNG bytes, and decoded RGBA8 entries represented by `ThumbnailPathLookupEntry`, `ThumbnailPngBytesLookupEntry`, and `ThumbnailRgba8LookupEntry`; RGBA8 entries expose decoded pixel bytes through `pixels()`. Consuming `into_parts()` methods on public multi-field owned values return `#[non_exhaustive]` named parts structs with public fields instead of tuples, so callers can move values by field name while the library retains room to add fields. Single-value consuming accessors such as `InstalledThumbnailPath::into_path_buf()` may return the single owned value directly.

The public error enum is non-exhaustive so new diagnostics can be added without forcing a major compatibility boundary. Public `ThumbnailError` reason strings are diagnostic text for humans and logs, not stable machine-matchable values; callers that need control flow should match structured variants and typed problem values instead. Result and state enums that callers normally match to drive behavior are also non-exhaustive so new externally visible states can be added without forcing a source-incompatible public API boundary: `ThumbnailSize`, `CacheNamespace`, `PersonalThumbnailLookup`, `SharedThumbnailLookup`, `PersonalValidationOutcome`, `SharedValidationOutcome`, `CacheEntryInspectionOutcome`, `SharedCacheEntryOutcome`, `SharedThumbnailMetadataPolicy`, `NonstandardEntryPolicy`, `OriginalUriIdentity`, `AccessTimePreservation`, `ThumbnailPngBitDepth`, and `ThumbnailPngColorType`. `CacheEntryProblem` remains non-exhaustive because new problem facts may be added without changing the high-level outcome states. Metadata-specific entry problems are carried as `CacheEntryProblem::Metadata(ThumbnailMetadataProblem)`, where `ThumbnailMetadataProblem` identifies the affected `ThumbnailMetadataKey` (`Uri`, `Mtime`, `Size`, or `MimeType`) and the `ThumbnailMetadataProblemKind` (`MissingRequired`, `InvalidSyntax`, or `ValueMismatch`). Non-metadata entry facts such as unreadable entries, unverifiable originals, PNG conformance failures, nonstandard filenames, and URI filename mismatches remain direct `CacheEntryProblem` variants. `RawThumbnailPixelFormat` is non-exhaustive so future raw pixel formats can be added without making the current format enum a breaking boundary. Public owned result types that directly carry PNG or pixel buffers, including `ThumbnailPngBytesLookupEntry`, `ThumbnailRgba8LookupEntry`, and `InstalledThumbnailPngBytes`, must not expose `Clone`; callers that need shared ownership can wrap returned buffers explicitly. The current library problem vocabulary does not include `OriginalMissing` or `UnreadableOriginal`; personal lookup and write APIs require caller-confirmed original identity, while inspection APIs report cache-entry facts without opening originals.

`ThumbnailSize::all()` returns a borrowed static slice of currently supported standard sizes in cache scan order. The return type intentionally does not expose a fixed array length contract; callers should iterate the slice or copy it into their own collection when they need ownership.

## Original Identity Boundary

Original identity selection is intentionally split between the library and the caller. The library owns canonicalization for identities whose semantics are part of this project: absolute local path bytes, textual local `file:` URI input, and shared-repository direct-child filenames. For non-local, virtual, KIO-style, archive-entry, resolved-playback, temporary-extraction, or application-specific sources, the caller chooses the stable absolute original identity URI because only the caller knows which URL represents the user-visible original rather than an implementation detail. The caller-selected constructor is not a local-file URI constructor and must reject `file:` identities; callers with local file URI text must use the dedicated local `file:` URI constructor. The library must validate that a caller-selected value can be used as absolute thumbnail URI identity text, reject relative references, control characters, and unescaped non-ASCII IRI text, and then preserve the accepted bytes exactly for filename hashing, `Thumb::URI`, and metadata comparison. This validation is not a promise to implement full RFC URI parsing or scheme-specific normalization. `OriginalIdentity` names the URI together with the freshness and write facts required by the Freedesktop cache contract: canonical personal URI, modification time, optional original byte size, and optional MIME type. `OriginalIdentity::new(uri, mtime)` creates the required identity facts, `with_original_byte_size(size)` adds optional byte-size metadata fluently, and `with_mime_type(mime_type)` validates and adds optional MIME metadata fluently. The MIME setter is the fallible operation because it validates PNG text metadata constraints. It is not a URI-only identity type; URI-only values remain represented by `PersonalOriginalUri`, `SharedRelativeOriginalUri`, and `OriginalUriIdentity`. URI and namespace newtypes implement conventional borrowed conversions where unambiguous: `PersonalOriginalUri`, `SharedRelativeOriginalUri`, and `FailureNamespace` implement `AsRef<str>`; `SharedRelativeOriginalUri` and `FailureNamespace` implement `FromStr`; `PersonalOriginalUri` intentionally does not implement `FromStr` because local file URI canonicalization and caller-selected non-file URI preservation are distinct constructors. The library must not fetch, mount, resolve, parse and reserialize, or scheme-specifically canonicalize caller-selected non-local identities as a hidden step.

Application lookup and validation may read existing thumbnail cache PNG files, parse their metadata, and return cache-entry facts, cache paths, or caller-requested thumbnail bytes. That cache lookup is separate from source acquisition: the library must not open a non-local original URL, read an archive member, follow a resolved playback path, or decode source media to prove freshness. For non-local and virtual backends, the caller supplies backend-confirmed readability, current modification time, optional `original_byte_size`, and optional MIME type when it needs a display-valid lookup result or a write identity.

## Cache Lookup Surfaces

The library should expose a computed path API and three distinct validated lookup output surfaces. The computed path API accepts an already accepted thumbnail URI identity and namespace, resolves the relevant cache root, and returns the cache path that would contain the thumbnail. It must not read the filesystem and must not imply that the file exists, is valid, is safe to display, or still belongs to the current original. This surface is for diagnostics, dry-run output, reports, and install targeting. The personal-cache method name is `cache_entry_path` to avoid implying a personal-only semantic distinction; shared repositories expose path calculation through their explicit repository context.

A validated path API opens the candidate cache PNG without following symlinks, verifies identity metadata, freshness metadata, PNG conformance, and namespace dimensions against the caller-provided original identity, and returns a path only when the entry is display-valid at validation time. This surface is useful for integrations that must pass a filesystem path to another toolkit component, but the contract must state that the caller accepts a replacement race if it reopens the path after validation. A missing path returns the lookup missing state. A symlink, non-regular cache entry, or no-follow open refusal returns the lookup invalid state with `UnreadableEntry`; unrelated I/O failures remain `ThumbnailError::Io`.

A validated PNG bytes API verifies the cache PNG opened without following symlinks and returns the exact validated PNG bytes together with the cache path and metadata facts when the caller requests PNG bytes output. This surface is for callers that want encoded cache content, want to defer decoding to their UI toolkit, or need exact bytes for transfer or comparison. A validated RGBA8 API verifies the same cache PNG and returns decoded pixel data together with the cache path, width, height, stride, and metadata facts when the caller requests `rgba8` output. `rgba8` is not PNG file content; it is a tightly packed row-major decoded buffer with `stride == width * 4`, byte order `[red, green, blue, alpha]`, and straight/unpremultiplied alpha. The RGBA8 API decodes only PNG files that already pass validated lookup conformance: 8-bit, non-interlaced `Rgba` PNG data is copied into the output buffer, and 8-bit, non-interlaced `GrayscaleAlpha` data is converted to `[gray, gray, gray, alpha]`. RGB without alpha, indexed, grayscale without alpha, 16-bit, interlaced, and other nonconforming PNG encodings remain invalid lookup results with `NonconformingPngFormat`; the RGBA8 API must not permissively add alpha or otherwise promote nonconforming PNGs to valid lookup results. Callers that only need a toolkit-consumable filename may request a validated path result instead and accept the documented replacement race. The public API should make output selection explicit, through separate methods or an output mode, so a caller asks for validated `path`, `png_bytes`, or `rgba8` instead of receiving an ambiguous union. Opened file handles, mmap-backed byte buffers, or other zero-copy representations are future optimization surfaces, not the initial display API. Personal-cache lookup APIs return `PersonalThumbnailLookup<T>` and must distinguish `Valid`, `Missing`, and `Invalid` outcomes; original readability and freshness facts are required before lookup, so unverifiable originals are constructor or request errors instead of personal lookup results. Shared-repository lookup uses the same explicit output split, but returns `FullyVerified`, `MetadataIncomplete`, `Missing`, `Invalid`, and `Unverifiable` states because caller-supplied freshness facts are optional and standard-allowed missing `Thumb::URI` or `Thumb::MTime` metadata is not equivalent to a fully verified personal-cache thumbnail. Shared-repository lookup APIs must require `SharedOriginalFacts` instead of repeated positional policy and freshness arguments. `SharedOriginalFacts::metadata_policy` determines whether missing standard-optional `Thumb::URI` or `Thumb::MTime` is accepted: `RequireComplete` treats missing metadata as `Invalid([MissingRequiredMetadata])`, while `AllowIncomplete` permits the standard-allowed incomplete metadata state and returns `MetadataIncomplete`.

## Generation Boundary

The base library API does not decode original source images, render documents, extract video frames, select thumbnailer helpers, perform source-aware scaling, preserve source aspect ratio from the original media, apply source orientation metadata, manage renderer temporary files, or decide when generation should be attempted. Source interpretation, including metadata such as Exif orientation and aspect-ratio-preserving scaling from the original media, belongs to the caller's renderer or external thumbnailer. The library may decode already rendered PNG bytes enough to enforce resource limits, collect metadata, normalize them into final Freedesktop cache PNG output, downscale rendered output to fit the requested cache namespace, encode explicitly described raw pixel buffers, write Freedesktop thumbnail PNG metadata, and atomically install personal-cache entries when the caller supplies rendered thumbnail data with a readability-confirmed original identity.

Personal-cache successful-thumbnail and failure-entry write APIs require a readability-confirmed original identity with an accepted thumbnail URI identity and a non-negative modification time in whole Unix epoch seconds. The library is not expected to prove readability for every possible URI scheme. Instead, write APIs should make the readability requirement explicit in the type or constructor used to create the write identity. For local `file:` originals, the library should provide a convenience constructor that first rejects non-absolute paths, then opens the original for reading and derives the canonical URI from the caller-supplied absolute path bytes and the modification time and optional `original_byte_size` from the readable file handle. This constructor does not resolve symlinks before constructing the cache URI identity; when the caller supplies an absolute symlink path, the cache URI preserves that symlink path while readability, modification time, and size come from opening and statting the referenced target. This constructor performs blocking filesystem I/O; async applications should call it from a blocking adapter such as a runtime-specific `spawn_blocking` equivalent rather than on an async executor worker. For non-local or virtual backends, callers that own the backend may provide an explicitly backend-confirmed readable identity containing the caller-selected stable URI identity, current modification time, optional `original_byte_size`, and optional MIME type. If the caller cannot confirm original readability or cannot obtain the original modification time, the library must reject a global personal-cache successful thumbnail or failure-entry write instead of creating an entry that violates the Freedesktop write preconditions or cannot be validated later. `Thumb::Size` and `Thumb::Mimetype` should be written when the caller supplies them.

Successful-thumbnail write APIs should accept caller-provided rendered PNG bytes. Callers that render to temporary files, including `.thumbnailer` `%o` outputs, remain responsible for managing those temporary files until the rendered output is handed to the library through a supported input form. The externally visible contract is that the library treats this input as renderer output, not as the original source file.

Successful-thumbnail write APIs must install only Freedesktop-conforming final PNGs. The library owns normalization from supported rendered PNG bytes to the final cache format: 8-bit, non-interlaced RGBA PNG with full alpha support, thumbnail metadata, and dimensions within the requested namespace. When supported rendered PNG output is larger than the requested namespace, the library should downscale the rendered output to fit the namespace while preserving the rendered image's aspect ratio, instead of failing solely because the renderer wrote a larger PNG. The library must reject non-PNG bytes, invalid PNG structure, unsupported PNG features, normalization failures, resource-limit failures, and final dimension violations with precise diagnostics. The PNG parser and validation paths must check decoded output buffer size and pixel count before allocating decode buffers; direct parse APIs report resource-limit failures as `ThumbnailError::ResourceLimitExceeded`, while validation and inspection APIs report them as `CacheEntryProblem::ResourceLimitExceeded`. The normalization path must not decode original source formats, interpret source color-management or orientation metadata as source semantics, select animation frames from animated PNGs, or repair aspect-ratio mistakes made by the renderer.

Successful-thumbnail write APIs should also expose a narrow raw-pixel install surface for callers that already own rendered `RGB8` or `RGBA8` buffers. Raw install inputs must include an explicit pixel format, width, height, stride in bytes, and pixel slice; the library must never infer raw format from byte length. The only supported initial raw pixel formats are `RGB8` and `RGBA8`. `RGB8` input is converted to RGBA with alpha `255`; `RGBA8` input preserves the supplied alpha bytes. Stride may include row padding, and conversion must skip padding according to the caller-supplied stride. Raw conversion must not perform premultiplied-alpha conversion, color management, YUV conversion, 16-bit conversion, source format decoding, or heuristic format detection.

Raw image constructors must reject zero width or height, dimensions or decoded byte sizes that exceed the same rendered-thumbnail resource limits used by PNG normalization, stride values smaller than `width * channels`, buffers shorter than `stride * (height - 1) + width * channels`, and integer overflow. These failures are reported as unsupported rendered thumbnail input before any cache file is written. Accepted raw input is converted into the same internal RGBA8 representation used by rendered PNG normalization, then uses the shared final downscale, metadata writing, final PNG validation, and atomic personal-cache install path. Oversized raw images should be downscaled to fit the requested cache namespace while preserving the raw rendered image's aspect ratio.

Borrowed raw image values expose validated `width`, `height`, `stride`, `format`, and `pixels` accessors. Owned raw image values expose the same accessors plus `into_parts` returning a named parts struct so async adapters and higher-level queues can inspect or move the validated buffer without reconstructing it; `as_borrowed()` remains the bridge into the borrowed raw install surface. Owned types that directly carry rendered bytes or raw pixel buffers must not expose `Clone`, because cloning them can duplicate large image buffers unexpectedly.

Successful install APIs should use the same explicit path-or-PNG-bytes output selection as lookup APIs. A path install API returns only the installed cache path. A PNG bytes install API returns the installed cache path and final normalized PNG bytes. Returned bytes must represent the final cache entry after metadata writing and normalization, not the renderer input bytes, because the library may rewrite the image before atomic publication. Failure-entry writers use the same explicit path-or-PNG-bytes split. Opened file handles for installed entries may be added later as an optimization, but the initial caller-selectable outputs are path and PNG bytes.

The library should also expose owned request APIs for callers that wrap the blocking core in async or runtime-specific adapters. These request types own the cache root or shared repository context, original identity, thumbnail size selection, optional freshness facts, and any rendered PNG bytes needed by the operation, while preserving the existing borrowed sync methods as the canonical zero-extra-allocation surface for direct callers. Request constructors must only assemble values and must not perform filesystem I/O; filesystem reads, writes, validation, inspection, and normalization happen only when an execution method such as lookup, install, failure-entry write, or inspection is called. Owned request constructors should not be `const fn` unless the API is prepared to preserve that promise permanently; ordinary constructors leave room for future validation or normalization while still performing no I/O. Owned request execution methods consume `self`, so a runtime adapter can pass `move || request.install_png_bytes()` or equivalent directly to `spawn_blocking` without cloning bytes. Owned result types expose explicit consuming accessors such as `into_parts` and `into_path_buf` for adapters that need to move paths, metadata, or PNG bytes across task boundaries; multi-field `into_parts()` returns named parts structs, while one-field accessors can return the single moved value directly. The crate must not add Tokio or any other async runtime dependency for this wrapper layer.

Write APIs must create missing standard personal-cache directories with mode `0700`, install final thumbnail files with mode `0600`, write temporary files in the destination directory, and publish final entries with an atomic rename. Existing standard personal-cache directories must be owned by the current user and must not grant group or other access; directories that fail this privacy check are rejected with an explicit insecure-cache-directory diagnostic. The initial library API must not silently rewrite existing directory permissions. A future repair command may be added only after its user-visible behavior is documented in `docs/spec/`. A write must not expose a partial thumbnail at the final cache path. The library must validate the final PNG against the requested namespace before installation, regardless of the supported rendered input form.

For personal-cache validation, missing `Thumb::URI`, a `Thumb::URI` value that differs from the canonical original URI, missing `Thumb::MTime`, or a `Thumb::MTime` value that differs from the original modification time in whole seconds makes the thumbnail invalid for display. `Thumb::Size` should be compared when present. Management tools should distinguish missing required metadata and invalid metadata syntax from metadata that is well-formed but stale for an existing original.

For shared-repository validation, `Thumb::URI`, `Thumb::MTime`, and `Thumb::Size` should be compared when present. Missing `Thumb::URI` or `Thumb::MTime` should produce policy-neutral validation and inspection facts that callers can evaluate with their own shared-repository freshness policy, but the library must not report such an entry as equivalent to a fully metadata-validated personal-cache thumbnail. Public validation result types must be context-specific: personal thumbnail and failure-entry validation return `PersonalValidationOutcome::{FullyVerified, Invalid}`, shared thumbnail validation returns `SharedValidationOutcome::{FullyVerified, MetadataIncomplete, Invalid}`, and personal cache inspection returns `CacheEntryInspectionOutcome::{Unchecked, Invalid}`. Shared lookup APIs must make the acceptance policy visible through `SharedThumbnailMetadataPolicy`. A lookup using `RequireComplete` declines shared thumbnails that are allowed by the Freedesktop standard when required freshness metadata is absent; a lookup using `AllowIncomplete` returns `MetadataIncomplete` for those entries. `validate_shared_thumbnail` remains policy-neutral and does not take a shared lookup acceptance policy.

Application validation APIs must not return an existing personal-cache thumbnail as display-valid when the caller cannot confirm that the original file is currently readable. For non-local backends, callers may provide an explicit original identity object containing the caller-selected stable URI identity accepted by the library, current modification time, optional `original_byte_size`, and proof that the original was readable through that backend. The same readability-confirmed identity model should be used by personal-cache write APIs, while separate cache-inspection APIs for management tools may still parse thumbnail files and metadata without opening the original. Inspection APIs must report policy-neutral facts and must not present the entry as a validated thumbnail for display.

Failure entries are separate from successful thumbnail size namespaces. They are PNG metadata carriers stored under `fail/<program-version>/`; successful-thumbnail dimension limits do not apply to them. The initial failure-entry write API should not accept caller-rendered image bytes. Instead, it should create a deterministic minimal 1x1 transparent 8-bit non-interlaced RGBA PNG containing required `Thumb::URI` and `Thumb::MTime` metadata and optional original metadata supplied by the caller. The library can locate, parse, validate required personal-cache metadata, inspect, and explicitly write failure entries, but it must not decide when an application should record a failure, suppress future generation attempts, or delete failure state. Failure namespace values must be non-empty direct directory names: no `/`, NUL, control characters, `.`, or `..`. The initial public constructor should accept only ASCII letters, digits, `.`, `_`, `+`, and `-` so failure-entry writes cannot create nested paths or ambiguous namespace directories.

Cache namespace path fragments are exposed as `CacheNamespace::relative_directory()`, returning standard size directory names such as `normal` and failure directory fragments such as `fail/<namespace>`. `CacheNamespace` implements `Display` with the same string representation for logs and user-facing reports. It does not expose a generic `name()` method, because the value is a relative cache directory fragment rather than an opaque display name. Path newtypes implement conventional borrowed conversions where unambiguous: `PersonalCacheRoot` and `InstalledThumbnailPath` implement `AsRef<Path>`.

`ThumbnailMetadata` exposes both known-key accessors and raw iteration. Known-key accessors such as `thumb_uri`, `try_thumb_mtime`, `try_thumb_size`, and `thumb_mime_type` remain the preferred way to interpret standard metadata. `ThumbnailMetadata::iter()` returns all parsed raw PNG text metadata key/value pairs as borrowed strings so diagnostics, adapters, and management tools can preserve or display project-specific metadata without the library predicting every key.

The library should not apply user-facing cleanup policy. It may report facts such as unsupported original URI for local validation, missing required metadata, invalid metadata syntax, stored URI and filename hash mismatches, well-formed metadata mismatches, unverifiable original freshness facts, unreadable PNG structure, nonconforming PNG encoding, successful-thumbnail dimension violations, thumbnail timestamps, whether access time was preserved during metadata inspection, and cache location, but age thresholds, original existence probes, removable path heuristics, URI class names, reason vocabulary, and deletion decisions belong to the caller.

The library must not collapse all invalid entries into a single generic error state. A PNG that can be parsed but lacks full alpha support, uses interlacing, or exceeds the selected successful-thumbnail namespace dimensions is nonconforming for lookup, not equivalent to an unreadable PNG or invalid identity metadata.

The library removal API must operate only on cache entry handles returned by library iteration or explicit cache-path resolution. It must verify that the target is still inside the resolved thumbnail cache directory, must not follow symlinks, and must report deletion failures without retrying outside the cache root. `CacheEntryHandle::remove(self)` consumes the handle so a removal capability cannot be reused accidentally; `CacheEntryInspection::handle(&self)` supports read-only inspection, and `CacheEntryInspection::into_handle(self)` transfers the removal capability when the caller decides to delete the entry.

## Non-Goals

- Decoding source images, rendering documents, extracting video frames, selecting thumbnailer helpers, or scaling source content is not a base library goal; generation orchestration belongs in `xdg-thumbnail-generate` or other separate applications and crates that own thumbnailer execution or image, document, and video decoding stacks.
- Automatically deciding retry suppression, creating failure entries after arbitrary errors, or applying application-specific failure policy is not a base library goal.
- The initial library API does not create or update shared thumbnail repositories. Shared repositories are read-only inputs for lookup and inspection.
- A future explicit shared-repository creation mode may be added only after its externally visible behavior is documented in `docs/spec/`. That future mode must remain opt-in, must use the shared relative URI rules in `docs/spec/uri-canonicalization.md`, and must document a permission model that preserves the original file's intended visibility while explicitly calling out any security-motivated deviation from the Freedesktop shared-repository text.
